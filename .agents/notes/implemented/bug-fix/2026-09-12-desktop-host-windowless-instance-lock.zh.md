# Agent Note: 桌面宿主从无窗口进程手中收回单实例互斥体

Status: implemented

[English](2026-09-12-desktop-host-windowless-instance-lock.md) | 中文

## 问题

`desktop-host/Program.cs` 持有命名互斥体，使一个桌面宿主独占 WebView2 窗口，并把后续启动交给已拥有它的进程。当该进程没有主窗口时——崩溃残留，或在窗口存在之前被打断的启动——这次交接什么也没做。于是后续启动在毫无显示的情况下退出，而残留进程继续持有互斥体，之后每次启动都重复同样的静默退出，直到用户在任务管理器中结束该进程。

## 决策

`ActivateExistingWindow` 现在返回是否抬起过窗口。同名但无窗口的进程会被就地终止（`Kill(entireProcessTree: true)`），随后本次启动最多等待互斥体两秒。被终止的持有者释放的是被遗弃的互斥体，因此 `AbandonedMutexException` 是这次等待的预期结果，并让本进程持锁；等待超时则退出，而不是启动第二个宿主。被终止进程的服务器子进程随它一起结束——子进程在生成时被放进 kill-on-close 作业对象——因此恢复过程不会在端口上留下孤儿服务器。

`AppWindow.FormClosed` 会释放 WebView 并调用 `Environment.Exit(0)`。窗口关闭即结束进程，这正是"互斥体仅在存在窗口期间被持有"这条不变量的保障，而恢复路径依赖它。

## 曾考虑的替代方案

**等待无窗口进程稍后发布窗口。** 否决：窗口创建已经失败的启动不会在之后产生窗口，等待只会阻塞，然后以与之前完全相同的方式失败。

**枚举进程的顶层窗口，而不是读取 `MainWindowHandle`。** 否决：这轮 P/Invoke 扫描能拿到的是隐藏窗口与尚未创建的窗口，交接都无法使用，而真正要紧的情形——完全没有窗口的进程——两条路都够不到。

**用记录 PID 的锁文件追踪实例。** 否决：内核在持有者死亡时释放互斥体，而锁文件需要自己的一套存活判定来处理 PID 复用与残留文件，并且仍要面对同一个问题：如何处理已死的持有者。

## 后果

发现同名无窗口进程的启动会不经确认地终止它，因此那个进程中未完成的任务会失去它的服务器子进程。互斥体等待上限为两秒，因此持有互斥体却无法被终止的进程仍以静默退出收场——用户看到的结果与之前相同。这条路径没有任何自动化覆盖：`desktop-host/` 没有测试工程，且该行为属于 Windows 进程生命周期，因此验证方式是 `dotnet build desktop-host/DeepSeekHarness.csproj`，外加在存在无窗口同名进程时手动启动。
